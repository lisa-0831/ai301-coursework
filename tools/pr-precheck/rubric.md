# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | The changed-file list and complete diff, compared with the plan's stated files, implementation approach, test plan, and recorded deviations. | Pass if the substantive changes remain within the planned scope, including explicitly justified deviations. Necessary supporting changes are acceptable when their relationship to the issue and plan is clear. Fail if the diff silently changes unrelated behavior, omits a material planned implementation without disclosure, or contradicts a claim of exact plan fidelity. | required |
| issue-alignment | The issue context and reproduction evidence, compared with the changed behavior visible in the diff and the PR summary. | Pass if the implementation addresses the issue's supported problem through a plausible, relevant change, without introducing a separate feature or unrelated redesign. The evidence need not prove perfection, but it must connect the change to the reported failure. | required |
| test-evidence | The test evidence section (printed command output, recorded reproduction results, and stated test runs), the regression tests added or changed in the diff, and the testing claims in the PR description. | Pass if the central fix is verified by observable evidence: either printed command output, or a specific reproduction record (the issue's exact trigger plus a concrete, state-distinguishing after-result matching the plan's expected after-state) corroborated by an issue-specific regression test in the diff that asserts that same behavior and falls within a stated test run. Complete raw logs are not required when this combination lets a reviewer assess the change, and for GUI/TUI behavior a written action sequence with the exact visible result is the native record. Failed, incomplete, or unavailable checks are acceptable when their actual outcomes and relevant limitations are clearly disclosed. Fail if verification rests only on generic success claims ("works now", "tests pass"), placeholders, test source with no specific reproduction record or printed run, or invented success. Adding a test or asserting that tests pass is never sufficient by itself. | required |
| test-coverage | The plan's test strategy and reproduction steps, compared with tests added or changed in the diff and the before/after results in the test evidence. | Pass if the evidence verifies the issue's essential behavior on the issue's own trigger (not a control or an unchanged path) and reasonably accounts for the material cases promised by the plan. The after-state may be shown by printed output or by a specific reproduction record corroborated as `test-evidence` describes; the before-state may come from the plan's repro evidence. An issue-specific regression test whose assertions encode a planned case, an equivalent test, or a transparently explained limitation may satisfy that case when enough evidence remains to assess the fix. Fail if a critical promised case is silently omitted or the available tests do not exercise the affected behavior. | required |
| diff-quality | The complete diff and changed-file list, compared with the issue's scope and the repository's stated contribution expectations. | Pass if the change is sufficiently focused and reviewable, with no material debug statements, accidental files, commented-out code, unrelated refactors, or other debris that obscures the fix. Do not reject harmless formatting or necessary supporting edits merely because they add lines. | required |
| claim-accuracy | Every substantive claim in the PR title, summary, change list, testing section, and reviewer notes, compared with the plan, diff, and test evidence. | Pass if the description accurately represents what was changed, tested, omitted, or left uncertain. A behavioral claim is supported when the diff implements it and printed output, a specific reproduction record, or an issue-specific regression test assertion within a stated run shows it. A specific secondary claim (a named suite or lint run with its scope or counts, generated files unchanged) that nothing contradicts and that is not the sole support for the central fix is recorded as unverified but does not fail this check. A disclosed shortfall is not automatically a failure. Fail if the PR claims a fix, test, or behavior that the diff or evidence contradicts or leaves entirely unsupported, claims completeness or unchanged behavior that the artifacts contradict, or hides a material contradiction between its description and the artifacts. | required |
| repo-standards | The candidate PR title and description, compared with the repository's PR template, contributing instructions, and any explicit policy or disclosure requirements in the package or live repository. | Pass if all applicable substantive repository requirements are met, including required issue references, meaningful template sections, and AI-use disclosure where requested. An honestly marked N/A is acceptable for an inapplicable section. Do not invent requirements absent from the supplied standards or reject solely for cosmetic differences. | required |

## Verdict rule

Grade every check as `pass`, `fail`, or `unclear`, using its stated evidence and pass condition.

Return `accept` only when every required check is `pass`.

Return `reject` if any required check is `fail` or `unclear`. An `unclear` grade means the evidence is insufficient to verify that the pass condition holds; missing proof must not be treated as success.

Checks marked `preferred`, if introduced later, provide feedback but never change the verdict.

Always evaluate all checks, even if an earlier required check fails. Record a concrete supporting observation or missing evidence for each grade. Do not introduce additional rejection conditions outside this rubric.

An honestly disclosed limitation is not automatically grounds for rejection. Judge whether the remaining evidence satisfies the actual pass conditions, rather than requiring every check command to succeed or every planned detail to be implemented without exception.
